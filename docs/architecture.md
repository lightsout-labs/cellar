# Architecture

Status: Approved

How Gridworks is built. What it must do is in
[requirements.md](requirements.md). Reasons for the decisions that are costly
to reverse are in the ADRs under `docs/adr/`.

## Overview

Gridworks is a static single-page application in two parts. The **engine** is
plain TypeScript with no DOM dependency: it owns the workbook, executes
every edit as a command, recalculates formulas, and reads and writes files.
The **app** is the browser side: a canvas that draws the grid, React
components for everything around it (ribbon, formula bar, sheet tabs,
dialogs), and one platform module that is the only code allowed to touch
files, storage, the clipboard and printing. When the user types in a cell,
the grid passes the text to the app, the app sends a `setCell` command to
the workbook, the workbook parses the input, stores it, records the inverse
for undo, marks dependent cells dirty and notifies its listeners; the grid
repaints the visible cells, reading each one from the workbook (which
calculates a dirty cell when it is read), and the app asks the platform to
record the command in browser storage at once and to save the changed
sheet a moment later.

## Stack

| Concern | Choice | Why |

| `.csv` | Our own reader and writer | About a hundred lines; no dependency justified (R32). |

| Browser storage | IndexedDB, used directly | Holds large workbooks; the few calls needed do not justify a wrapper (R33). |
| Offline | A service worker generated by `vite-plugin-pwa`, with no web app manifest | Precaches the build output (R35); installable PWA packaging is out of scope. |
| Translation | Our own `t(key)` over two dictionaries | Two languages and plain strings need no library (R41). |
| Unit tests | Vitest, Node environment for the engine | Running the engine tests in Node demonstrates R50. |
| End-to-end tests | Playwright on Chromium, Firefox and WebKit | The supported browsers (Constraints). |
| Lint and format | ESLint, Prettier, `tsc --noEmit` | ESLint also enforces the module boundaries below. |
| Package manager and runtime | npm and the current Node.js LTS, pinned in `.nvmrc` | The default; nothing needs more. |
| Hosting | GitHub Pages, deployed by GitHub Actions | Constraint (R49). |

There is no state management library: the workbook is the store, and React
reads it with `useSyncExternalStore`.

## Modules

Each module has a small interface and hides substantial behavior. Tests go
through the interface only. Every module, layer, and dependency is here
because a requirement needs it.

|---|---|---|

Boundaries, enforced by the build so that R50 and R51 cannot erode:

- `src/engine` compiles with its own `tsconfig` that excludes the DOM
  library, and ESLint forbids it from importing `src/app`.
- ESLint forbids `indexedDB`, `localStorage`, `navigator.clipboard`,
  `window.print`, file inputs and download links everywhere except
  `src/app/platform/web`. A desktop shell such as Tauri or Electron would
  add a second implementation of `Platform` beside it and reuse everything
  else.

Decisions that are cheap to reverse, with their reasons:

- **Every edit is a command.** Before it runs a command, the workbook
  records the contents and styles of the cells the command will change as
  a `restore` command, which puts them back, so undo covers every change by
  construction (R5) rather than feature by feature. A change to the sheets
  (add or duplicate, delete, rename, recolor, move) records its own
  reverse: deleting a sheet records a `restoreSheet` command holding a
  snapshot of it, and the others their opposite. Undo runs that
  command and records its own reverse for redo; the listeners receive it
  like any other, so storage records an undo as a change. The workbook
  keeps the last 100 changes, Excel's number, and a new change forgets
  what could be redone. A workbook opened with its recorded changes
  replayed (`fromSnapshot(snapshot, changes)`) starts with nothing to
  undo, as the history is not stored.
- **The view follows the sheets.** `View` subscribes to the workbook when
  it is made, right after the workbook and before anything else, so that
  when the sheet it shows is deleted, by a command or an undo, it shows the
  sheet that took its place before any other listener reads the deleted
  one. Switching to another sheet selects A1 there; each sheet's selection
  is not remembered.
- **Window shortcuts are handled on the window**, not by the grid, so that
  Ctrl/Cmd+Z and Ctrl/Cmd+Y work after a click on the ribbon too. During an
  entry they are left to the editor, which undoes its own typing.
- **Recalculation follows a dependency graph.** Each sheet keeps, for
  each cell, the formulas that read it alone, and for each column, the
  formulas that read a range over it (a whole row is in every column). A
  change marks the formulas that read the changed cells, and theirs in
  turn, as needing calculation; a formula is calculated when it is read,
  after the ones it reads, with an explicit stack (ADR 0004). Nothing else
  is calculated, and `calculations` counts what is, so tests check it
  (R14). Cells that nothing reads stay uncalculated until read.
- **Circular references give 0 and are reported**, as in Excel without
  iteration. The workbook calculates every formula a change sets, and the
  formulas that were in a circular reference, before it tells its
  listeners, so `circularReference()` knows every one; the status bar
  shows a cell of it as `Circular References: B1`, with its sheet when
  another sheet is shown (R15). A stored workbook calculates all its
  formulas when it opens.
- **References to other sheets are by name**, as written. Renaming a
  sheet rewrites the formulas that name it; a reference to a sheet that
  no longer exists gives `#REF!` but keeps its text, so undoing the
  deletion brings it back (Excel writes `#REF!` into the text). Any change
  to the sheets other than a color or the order finds again what every
  formula reads and recalculates every formula. A rename also rewrites
  references left from a deleted sheet of the same name, which an undo of
  the rename then does not put back.
- **Formulas are stored as Excel writes them**: function names and
  references in capitals, sheet names as the sheets have them, without
  spaces other than the intersection operator.
- **A range where one value is expected gives the cell in the formula's
  row or column**, Excel's implicit intersection, and `#VALUE!` when there
  is none; dynamic arrays are out of scope.
- **Cells are stored by column**, as arrays of values and of style
  identifiers, with formulas in a sparse map. Ten million populated cells
  (R45) do not fit in memory as one object each.
- **The grid scrolls natively.** An element that scrolls holds an element
  the size of the whole sheet at the zoom, and the canvas inside it sticks
  to the visible area and draws the cells under it on every scroll event.
  Wheels, trackpads, scroll bars and momentum then behave as everywhere
  else in the browser. The scroll position is that element's, not the
  `View`'s. It caps the sheet height: browsers limit an element to between
  about 17 and 33 million pixels, so a sheet has 100,000 rows of 24 pixels
  (4.8 million at 200%) and 100 columns, the numbers R1 states. More rows
  would need scroll bars of our own.
- **Selection is a list of ranges** with an active cell, and an anchor and
  focus for the last range, which Shift moves. A whole row, column or sheet
  is a range that spans the sheet, so the engine's `aggregate` sums any
  selection the same way.
- **Dates are Excel serial numbers** with a date format, as in Excel, so
  date arithmetic and `.xlsx` round trips need no conversion.
- **Typing sets a cell's format.** A typed date, time, percentage or
  number with separators sets the number format of its cell's style; a
  plain number keeps the format the cell has, and Delete clears values
  and formulas but not formats, as in Excel. The formula bar and the
  editor start from `editText`, which reads back as the same value.
- **Cells align by the type of their value**, as Excel's General
  alignment does: numbers right, text left, booleans and errors centered.
  Text that is too long runs over the empty cells to its right.
- **An entry has two modes**, as in Excel. Typing starts Enter mode, where
  an arrow commits and moves; F2, a double-click and the formula bar start
  Edit mode, where the arrows move the caret. Enter and Tab commit and
  move in both, and Tab therefore stays in the grid.
- **Number and date formats do not change with the interface language.**
  R41 covers the interface only; one behavior keeps files and tests the
  same in both languages. Function names stay in English in both languages,
  as they are in `.xlsx` files.
- **A theme is a set of CSS custom properties**, chosen by the `data-theme`
  attribute of the root element, and every color of the interface is one of
  them (R42, R43). The canvas reads the same properties when it paints and
  repaints when the attribute changes, so the grid needs no theme of its
  own.
- **The ribbon grows with the features.** A tab or control is added by the
  slice that builds its feature, so none is ever a placeholder (R44).
- **Files are opened with a file input and saved as a download.** It works
  in all four browsers; the File System Access API does not.
- **Opening a file makes a new stored workbook**, under a new identifier,
  and the preference `workbook` names it as the one to show at the start;
  the workbook shown before stays stored, for the start screen to list.
  Until then, the workbook shown at the start is the one opened last, or
  the one with the identifier `default`.
- **A file opened is read as far as Gridworks supports it.** A formula
  that does not parse, or calls a function or name that Gridworks does not
  have, is replaced by its last result. Charts, pivot tables and pictures
  are counted from the file's parts and left out, and so are cells beyond
  the 100,000 rows and 100 columns of a sheet. A message bar under the
  ribbon lists what was left out (R31), or says that a file is not a valid
  `.xlsx` file, which leaves the workbook shown as it was, or that a save
  failed. The other
  features of R30 are read by the slices that build them, and until then
  are left out without a word. A file saved by Gridworks has no formula
  results in it, and asks to be calculated when it is opened.
- **Cell fonts are a fixed list of fonts present on all three desktop
  systems**, with fallbacks, so that nothing is downloaded.
- **Printing builds a plain HTML table** of the sheet or selection with
  print CSS for page size, orientation and margins, and rows that do not
  break across pages (R36). The canvas itself cannot be paginated.

## Data

A workbook **snapshot** is a versioned, JSON-compatible object: workbook
properties (name, sheet order, named ranges, the table of distinct styles)
and, for each sheet, its name and tab color, its columns of values, style
identifiers, formulas, row heights and column widths, merges, frozen
panes, filters, validation rules, conditional formats, notes and
hyperlinks. It is the only form in which a
workbook leaves the engine.

- **Browser storage**: an IndexedDB database named `gridworks` with three
  object stores. `workbooks` holds one record for each workbook
  (identifier, name, modification time, workbook properties). `sheets`
  holds one record for each sheet, keyed by workbook and sheet identifier,
  so that autosave can rewrite only the sheets that changed; for now it
  rewrites them all, after deleting those of the workbook, so that a
  deleted sheet leaves no record. `changes` holds
  each command executed since the workbook was last saved, keyed by
  workbook and sequence number. Each command is recorded the moment it is
  executed; the whole workbook is saved half a second after the last change
  and when the page is hidden, and that save deletes the changes it
  includes. Opening a workbook replays its changes over its last save.
  A save cannot be started while the page unloads: browsers discard an
  IndexedDB transaction that begins then. See
  [ADR 0005](adr/0005-record-each-change-then-save-snapshots.md).
- **Preferences** (language, theme): through `Platform.preferences`, stored
  in `localStorage` by the web implementation, under `gridworks.language` and
  `gridworks.theme`; `gridworks.workbook` names the workbook to show at the
  start. Without a stored choice the language is that of the
  browser and the theme that of the system.
- **Files**: `.xlsx` and `.csv`, converted to and from a snapshot by
  `engine/io`. Undo history is not stored.

## Repository layout

```
src/engine/value.ts      The value types shared by the engine modules
src/engine/workbook/     Workbook model, commands, recalculation, undo
src/engine/formula/      Parser, evaluator, function library
src/engine/format/       Number formats and input recognition
src/engine/io/           XLSX and CSV
tests/xlsx.ts            Builds .xlsx files laid out as Excel writes them, for tests
src/app/platform/        Platform interface
src/app/platform/web/    The web implementation
src/app/grid/            Canvas grid and the view state
src/app/ui/              React shell, dictionaries, themes
src/main.tsx             Entry point: creates the web platform, mounts App
tests/e2e/               Playwright tests
tests/boundaries.test.ts Checks that lint enforces the module boundaries
scripts/check-docs.py    Document checker, copied from nightshift
docs/                    Requirements, architecture, ADRs, backlog
.github/workflows/       CI and deployment
```

Unit tests sit beside the code they test, as `*.test.ts`. In `src/app`, code
that touches the DOM is in `.tsx` files or in `src/app/platform/web` and is
covered by the end-to-end tests; every other `.ts` file there has no DOM, is
unit tested, and counts toward the coverage floor.

## Testing

| Level | Covers | How |
|---|---|---|
| Unit | The engine through its four interfaces: every command and its undo, every function against results taken from Excel's documentation, reference rewriting, recalculation and its time limit (R46), number formats, XLSX and CSV round trips and the 10 MB open time (R47) | Vitest in the Node environment, with no DOM available |
| Unit | App logic that needs no browser: grid geometry, selection and keyboard navigation, the status bar summary, translation completeness for both languages, shortcut tables, the printable document | Vitest |
| End to end | Each slice's user flow in the built app: keyboard and mouse on the grid, the ribbon, menus and dialogs, storage across reloads, file open and save, both themes and languages, offline use | Playwright on Chromium, Firefox and WebKit |
| End to end, Chromium only | The system clipboard (R7), and scrolling speed (R45), measured as the time to draw each frame, one scroll step a frame, while scrolling a sheet of 100,000 by 100 populated cells stored directly in IndexedDB; every frame must draw within 16 ms | Playwright |
| End to end | Recalculation time (R46): a chain of 100,000 formulas, stored directly in IndexedDB as for R45, whose start is edited | Playwright |

Two requirements cannot be fully checked by automated tests and are checked
by the human at release acceptance: that files saved by Gridworks open in
Microsoft Excel itself (R30), and the 60 frames per second on a mid-range
laptop (R45). The automated tests cover them as far as they can: files
built by `tests/xlsx.ts` with the parts and markup that Excel writes,
round trips through the writer and reader, and a frame-time budget with
headroom for CI machines.

## Deployment

The app runs at `https://lightsout-labs.github.io/gridworks/`. A GitHub Actions
workflow runs on every push to `main`: it builds the production bundle with
the base path `/gridworks/`, publishes it with the GitHub Pages actions, and
then runs one Playwright smoke test against the live address, which loads
the app, enters a formula and checks the result. It is the end-to-end test
tagged `@smoke`, run with `GRIDWORKS_URL` set to the live address and
`GRIDWORKS_COMMIT` to the deployed commit, which the test waits to be served. A failed smoke test fails
the workflow. A release is verified by that smoke test and by the human's
acceptance of the deployed app.
